# Project agent instructions

## Repository map and validation

- Setup and contribution flow: [CONTRIBUTING.md](CONTRIBUTING.md); current downloads: [docs/releases/current.md](docs/releases/current.md).
- Java Core, adapters and MCP: `src/main/java/dev/copperbench/`; tests mirror these packages in `src/test/java/dev/copperbench/`. Run the relevant Gradle test classes; public Java API changes also need `javadoc`.
- UI: `ui-shell/src/` and `ui-shell/e2e/`; use `npm test --prefix ui-shell`, the UI build and affected Playwright cases. Shared contracts live in `ui-core/schemas/v1.0/`; validate them with `npm test --prefix ui-core`.
- Python SDK: `sdk/python/`; run `python -m unittest discover -s sdk/python -p 'test_*.py'`. Native/Core operation names come from the UI-Core schemas; MCP tool names come from `McpToolCatalog` and the running server's `tools/list`.
- TypeScript SDK: `sdk/typescript/`; after `npm ci --prefix ui-shell`, run `npm run test:sdk --prefix ui-shell` using the UI shell's TypeScript development dependency.
- Documentation: run `node scripts/verify-markdown-links.mjs`. The verification table in `CONTRIBUTING.md` gives commands by changed layer; source checks do not replace installed-product or gameplay evidence.

## Language and evidence

- Reply to the user in Chinese. Use English for commands and tool arguments when practical.
- Inspect the relevant source before changing behavior. Preserve unrelated working-tree changes.
- Distinguish observed runtime facts, tool receipts and model inferences. Report verification limits explicitly.

## Minecraft runtime validation

- For gameplay, controls, inventory, block interactions, persistence or in-game UI changes, perform relevant runtime validation with the `minecraft-control` MCP server when a test client is available. Compilation alone does not prove gameplay acceptance.
- Read `tools/minecraft-control-bridge/README.md` before first use. Follow its action, focus and evidence contracts.
- Project MCP registration is in `.codex/config.toml`. Codex launches the stdio server when connecting; do not start an extra background server or parallel input controller. The authorized computer-use focus recovery below is a sequential handoff. The input worker starts on the first desktop tool call. Before interacting with Minecraft, call `mc_doctor`, then `mc_list_windows`, and attach only the intended test client.
- If the tools are absent, inspect the project MCP configuration and report that the Codex MCP connection must be reloaded. A shell-launched stdio server alone does not register tools in an existing LLM session. Do not claim tool availability without a successful call. For missing dependencies, follow the README's project-venv setup.
- Launch the intended test client using the existing Copperbench lifecycle/SDK when needed; the bridge does not launch Minecraft. Keep the workspace lifecycle session alive. Confirm target process, game directory and test world; never pick the first Java window blindly.
- The lead LLM owns planning, code changes, menu-profile review, exception handling and acceptance decisions. For a calibrated menu flow, call `mc_menu_flow` once to enter the explicitly named world or save/quit; let the local state machine capture and check intermediate screens. Do not make another LLM/Jev round trip for each known menu button. Review the returned terminal image and receipt. Navigation completion is not gameplay acceptance.
- Menu profiles are built once from planner-inspected screenshots with exact world name, viewport size, language/theme and hashed image markers. Use `scripts/calibrate_menu_profile.py` in the bridge package. A matching profile can be reused across sessions. Do not invent labels/coordinates or calibrate from an uninspected image; recalibrate on changed layout. A profile failure is a request for inspection, never permission to weaken matching or click the first world blindly.
- `mc_menu_flow` is a bounded exception to per-step LLM screenshot review: at most six local batches (each <=2,000 ms / 32 actions), 25 seconds total, with fresh local visual guards before transitions. It only opens a filtered unique world, saves to title or quits; never creates/deletes worlds, approves dialogs or handles unexpected screens with guessed input. Check `mc_doctor` for the running version and supported flows before using them.
- Use `mc_observe`/`mc_step` for uncalibrated screens and gameplay. Jev is optional for genuinely unresolved local choices; do not add it to an action already decided by the planner or a deterministic menu flow. Using a second model alone does not imply a speedup.
- Start from an actual `mc_observe` image. The image returned by `mc_step` is also the next observation: inspect and reuse it instead of calling `mc_observe` again after every successful step. Reobserve if the frame expires, the window moves/resizes, the returned image is unavailable, or the state is uncertain. `mc_doctor` reports the running bridge version and frame budget in current releases; editing bridge source does not upgrade an already running MCP worker.
- Batch a short, predictable sequence into one `mc_step` (for example typing into an already observed chat box, Enter and a short wait), within 2,000 ms and 32 actions. Stop at an uncertain screen transition; do not run an unseen menu script or loop. Use explicit waits for known UI transitions, not extra model calls just to wait. Inspect the returned screenshot before the next decision. Reuse an `action_id` only to retrieve the identical action's receipt, never to repeat an action.
- If Jev can help with a local choice, provide a concise textual/structured summary containing the actual `frame_id`, `source: planner_visual_summary`, focus and uncertainties; supply a bounded goal and 2–32 meaningful candidate descriptions, including WAIT when appropriate. Jev does not see images. Review its choice before `mc_step`; it never executes input or verifies gameplay. On failure, report it and use explicit lead-LLM control or stop. Do not silently claim Jev was used.
- Before desktop interaction, finish independent source reads and prepare the bounded acceptance steps. During interaction keep decisions and tool payloads short; do unrelated analysis outside the control loop. Record end-to-end elapsed time, input/capture time, tool calls, rejected batches and Jev calls separately; do not infer a speedup from Jev latency or from fewer screenshots.
- Stop on focus loss, unexpected state, ambiguous targets or an exhausted task budget. Do not steal focus back repeatedly. F8 is the user emergency stop. Use `mc_stop` when necessary and `mc_detach` in cleanup, including failures; detaching does not close Minecraft.
- The user has authorized computer-use to recover focus before handing control back to Minecraft MCP. On focus loss, detach MCP input control, use computer-use to select the exact test window from current returned window objects, inspect its screenshot, and click a safe observed area to focus it. Then verify foreground state with `mc_list_windows` before reattaching; Minecraft navigation and gameplay remain with MCP. Do not run simultaneous input controllers, bypass MCP focus checks, or repeatedly steal focus. If computer-use cannot safely recover the intended window, ask the user to click Minecraft and leave it foreground without returning to reply. A normal client close may return `executed_unobserved`; confirm process exit, logs and the Copperbench task terminal state before declaring normal shutdown.
- The lead LLM records passed/failed/unverified with `mc_record_verification`, referencing actual screenshots and action/log evidence. Input success and Jev confidence are not proof of gameplay correctness. Report preparation commands separately from actual player interactions.
- Keep one shared bridge session per desktop. Store evidence under `output/minecraft-validation`. Do not put API keys in prompts, tool arguments, this file or committed configuration. On Windows the launcher accepts `TYPESAFE_API_KEY` or the current user's encrypted local credential; setup and rotation use `scripts/Set-JevKey.ps1` inside the bridge package.
