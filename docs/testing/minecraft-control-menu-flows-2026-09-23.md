# Minecraft Control 0.2.0 本地菜单流程验收

本轮将确定性菜单导航从逐按钮的主模型往返改为本地状态机。主模型审查一次界面模板并选择流程；`mc_menu_flow` 在同一输入 worker 内匹配中间画面、执行受限动作、等待下一状态，只返回终态或异常。没有把 Jev 加进这些已经确定的步骤。

## 实机结果

Windows、Fabric 1.21.1、Copperbench v18 导出包与随包 SDK、默认英文界面、854×480 客户区。沿用 `PRD17 Scene C v7` 专用测试世界，已校准模板直接复用上一轮真实截图，没有为了本轮逐步导航重新校准。

| 请求 | 实际路径 | 主模型导航调用 | 本地输入批次 | 工具计时 |
|---|---|---:|---:|---:|
| `enter_world` | 标题 → 世界列表 → 筛选完整名称 → 唯一结果核对 → 进入世界 | 1 | 3 | 8.324 秒 |
| `save_and_quit` | 游戏 HUD → 暂停 → 保存回标题 → Quit Game → 窗口消失 | 1 | 3 | 1.600 秒 |

两个流程共 2 次导航调用、0 次 Jev 调用。进入期间本地记录 20 个状态观察，退出期间 4 个；中间没有逐按钮的模型决策。进入终态只说明实际出现游戏 HUD，远处区块仍可能加载，不扩大为场景完全加载或玩法通过。

首次绑定未能取得前台焦点，流程在输入前返回 `FOCUS_LOST`，已 detach。用户恢复焦点后才进入上述正式会话；该准备失败单独保留，不纳入两次成功流程耗时。

退出最后一批的点击实际完成，后续短等待因窗口已消失产生嵌套 `interrupted / WINDOW_UNAVAILABLE`。流程返回 `window_closed_unverified`，不自行宣称正常退出。主 LLM 随后分别确认：

- 游戏日志记录 `PRD17 Scene C v7` 所有维度保存及 `Stopping!`。
- 本轮客户端 PID 37036 已消失。
- 产品任务 `b77295bc-05a2-45ee-a163-13e031d8761b` 为 `succeeded`，2026-09-22T16:57:27Z 结束（本地日期 9 月 23 日）。
- 34 个源码／定义／模型文件哈希前后一致，SDK 脚本自行退出，桥已 detach。

这证明该已校准菜单流程的实用效果；时间从工具内流程启动计到终态，不包含启动 Minecraft、一次校准、用户切焦点和主模型最终验收时间。上一轮约 9 分 33 秒包含其他输入与查询，不能与本表直接计算提速比例。

## 实现与保护

- [menu_flow.py](../../tools/minecraft-control-bridge/src/minecraft_control_bridge/menu_flow.py)：固定的进入／保存／退出状态机；在本地观察后才发送下一个动作。
- [MENU-FLOWS.md](../../tools/minecraft-control-bridge/MENU-FLOWS.md)：校准格式、MCP/Python 入口、适用边界与错误处理。
- [AGENTS.md](../../AGENTS.md)：已校准菜单优先单次流程；未校准界面和玩法仍由主模型逐步审查。

每批维持 2,000 ms／32 动作上限；整个流程最多 6 批、25 秒。焦点、F8、父进程存活、窗口身份／几何、幂等回执保持有效。错误世界名、多结果、模板内容变化和未知初始界面拒绝；过渡界面只轮询观察，不能通过重复点击推进。不创建或删除世界，不批准转换／备份等未知弹窗。

模板与视口、语言、字体/资源包有关。此版使用经过审查的图片区域匹配，不是任意版本、语言和分辨率上的通用 OCR；世界搜索文字当前仅支持可打印 ASCII。新场景应先校准，失败时检查画面，不能弱化匹配以强行通过。
