# Stage 17：v31 场景 A 的 Windows 双 Loader 验收

本轮完成 Windows Fabric / NeoForge 1.21.1 的“公开新建 → 结构化配置 → 修改 → 重开 → 生成 → 构建 → 隔离 JAR GameTest → 按验收任务导出”链。使用同一 v31 导出产品，主 JAR SHA-256 为 `c3b822d6deef37ac553f41358ee51c8e21996d378355d9f88b77927130abf499`。整体 PRD17 门禁仍开放。

## 输入与边界

两个工作区均由产品 `bootstrap create-workspace` 在明确授权的 `D:/Hyper-V/Stage17-Linux/final-acceptance` 下从空目录创建。分别为 `fabric-1.21.1` 和 `neoforge-1.21.1`；首次 SDK 查询均断言没有模组元素。使用随包 SDK，而非开发类路径或内部 Java 入口。

[复验脚本](../../scripts/stage17-structured-acceptance.py) 通过公开命令创建 `acceptance_forge`：硬度 3、抗爆 6、水平朝向、三槽库存、堆叠上限 64、破坏掉落、16×12×16 碰撞形状；另建未指定碰撞形状的 `default_cube`。将硬度改为 5，定义写入与重开读回一致。非法字符串硬度返回 `FIELD_TYPE_INVALID` 和字段路径，修订、定义及主源码哈希不变。

模型通过 `begin_blockbench_task`、`finish_blockbench_task`、`preview_blockbench_import`、`import_blockbench_task`、`bind_blockbench_model` 关联。输入是固定模型夹具和既有测试 PNG，只在任务编辑目录写入；没有手写 Java 修补模组实现，没有直接往生成模型目录写入资源。默认推导目标路径，模型绑定为 `stage17_structured:custom/acceptance_forge`。这是 API 模型回导证据，不冒充场景 C 的真实 Blockbench 编辑／导出。

测试源位于各工作区 `src/gametest/java`，通过公开 `prepare_game_tests` 创建模板后加入六个实际断言；`minimumTests=6` 对应下表六项，没有计入框架自检。源码快照和隔离宿主由产品 `run_gametest` 建立。模组实现源码没有复制进测试宿主。

## 证据与保留失败

- Fabric：`output/stage17-v31/scene-a-fabric-resumed/`；原始失败在 `scene-a-fabric/`。
- NeoForge：`output/stage17-v31/scene-a-neoforge/`。
