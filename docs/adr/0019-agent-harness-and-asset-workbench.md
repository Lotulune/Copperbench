# ADR-0019：定位为面向 Agent 的 Minecraft 验证与资产工作台

- 状态：提议，待项目所有者确认
- 日期：2026-11-16
- 细化：[ADR-0017](0017-native-first-agent-workbench.md)；调整 [ADR-0001](0001-fork-mcreator-as-the-product-base.md) 与 [ADR-0012](0012-bundle-and-own-the-fabric-generator.md) 的投入重心
- 待办落点：[维护清单](../remaining-work.md#下一阶段方向调整)

## 背景

1. **上游在补齐原有差异点。** MCreator 2026.3 EAP 的[更新日志](https://mcreator.net/changelog)（2026-11-16 读取）列出：可选的本机 MCP 服务及元素创建/编辑工具、NeoForge 26.3 的全量元素支持、26.3 的数据包与资源包生成器。本产品仍基于 2026.2.33518，Fabric 26.3 预览轨只有 5 类元素（`plugins/generator-fabric-26.3`）。
2. **结构化层是最贵的部分。** 8 个生成器、37 类元素的模板随每个 Minecraft 版本移植，而编写这类代码正是通用 Agent 进步最快的能力。
3. **ADR-0017 的决定没有落到默认路径。** 内置对话的系统指令仍要求先读 SDK、按字段契约创建元素；产品只能打开 `.mcreator` 工作区；当时计划的对照研究已终止，方向一直没有实测依据。
4. **独立数据包几乎缺席。** 0.1.20 的契约里没有数据包类型，新建流程不提供，生成器停在 26.1.x。类型和新建入口已随本 ADR 的同一组改动补上，其余见待办。
5. **流程偏重。** 12 周内 694 次提交、51 个标签、`evidence/` 2632 个文件；`feat` 64 条，`fix` 144 条。

## 依据：2026-11-16 小型对照实验

同一被试（Claude Opus 5.5，effort=high，每次运行为全新子代理）、同一台机器、同样的任务文本、同一个已预热的 Gradle 用户目录。任务与控制项见本地记录 `output/agent-comparison/2026-11-16/`（不入库）。目标均为 Fabric 1.21.1。

| 步骤 | 组 | 结束时上下文（token） | 工具调用 | 活动时长 | 构建失败/总数 | 结果 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| 搭建空工程 | 裸 Gradle | 95,938 | 30 | 394 秒 | 7/9 | 可构建 |
| 搭建空工程 | Copperbench（产品命令） | 0 | — | 76 秒、64 秒 | — | 两个工作区均创建成功 |
| T1 方块+物品+配方+双语 | 裸 Gradle | 70,399 | 6 | 79 秒 | 0/1 | 符合要求 |
| T1 方块+物品+配方+双语 | Copperbench | 209,146 | 66 | 704 秒 | 1/2 | 符合要求 |
| T2 自定义行为物品 | 裸 Gradle | 70,935 | 13 | 91 秒 | 0/1 | 符合要求 |
| T2 自定义行为物品 | Copperbench | 210,568 | 62 | 928 秒 | 1/2 | 符合要求 |

- **搭建是 Copperbench 的明确优势。** 产品约 1 分钟建好工作区，不消耗被试的 token。裸 Gradle 被试 9 次 Gradle 调用失败 7 次，其中 6 次是本机 Gradle 的 loopback 套接字问题，产品内部已经处理了这个问题。
- **创作阶段 Copperbench 组的成本约为 3 倍上下文、5 到 11 倍工具调用、9 到 10 倍时长，产物质量没有差别。** 四个产物都能独立重新构建（clean build 成功，jar 与被试产出逐字节一致），静态核对都符合任务要求。
- **两个任务里结构化元素都不够用，被试最后都转成了手写。** T1 的方块字段契约不能设置创造标签页、所需工具和掉落；配方元素的 ID 跟随元素名，方块占用 `ember_bricks` 后只能得到 `ember_bricks_recipe`，被试删掉配方元素改写 JSON。T2 的行为无法用元素表达。两次都把元素切换为手写归属，此后该元素的结构化编辑不再生成这些文件。
- **保护边界带来了绕行。** `update_workspace_file` 不能新建文件，生成的主类不可编辑，`import_asset` 需要桌面签发的授权而独立宿主拿不到，贴图只能直接写磁盘。T2 被试还报告物品的 `textureBase64` 字段被接受但没有生效。
- **发现一个产品缺陷。** Fabric 构建以 `cmd.exe /c gradlew.bat` 启动（`Fabric1211ProcessRunner`），依赖当前目录查找；父进程环境带有 `NoDefaultCurrentDirectoryInExePath=1` 时首次构建必然失败。两个 Copperbench 被试各因此失败一次。
- **两组都没有进游戏验证。** 产品已有的 GameTest 验收能力在默认指令下没有被任何被试使用。

**限制。** 每格只有 1 次运行，只有一个模型、一条版本轨道、两个小任务；任务规模不足以体现元素数量多了以后的引用治理和迁移价值。所有产物都没有进入游戏，“符合要求”指独立重新构建成功并通过对 jar 内容和源码的静态核对，不是玩法验收。“结束时上下文”是运行结束时的上下文规模，不是累计计费量。Copperbench 组的两次运行被用量额度中断后从原上下文恢复，表中的工具调用和活动时长是两段之和，恢复后的缓存失效可能拉长了时长。裸 Gradle 组的 T1、T2 直接得到了 loopback 问题的解法，并与 Copperbench 组共用同一个已预热的 Gradle 用户目录，这两点都对裸 Gradle 组有利。

## 决定

1. **定位。** Copperbench 是通用 Agent 与不会编程的创作者共用的 Minecraft 工作台，差异点是四件事：环境与工具链、构建到游戏内的验证回路、资产的可视化与治理、恢复点与权限边界。它不以“比 MCreator 多支持多少元素”或“替 Agent 写代码”作为目标。
2. **原生路线成为默认。** 内置对话和 Agent 文档默认让 Agent 直接编写工作区内的 Java、JSON 与资源，再用产品构建和验证；结构化元素、Procedure 图和模板是可选捷径，由 Agent 或创作者按需选用。生成源码与手写源码的归属保护不变，但新建手写文件和导入资产不应再需要绕开 Core。默认指令要把产品的验证能力（GameTest 验收）带进 Agent 的常规流程。
3. **结构化元素与模板生成器进入维护态。** 不再扩充元素类型和字段覆盖。新的 Minecraft 版本轨道以“可构建的工程模板 + 验证回路”为交付条件，不以结构化元素覆盖率为发布条件；NeoForge、数据包和资源包生成器优先同步上游，而不是自研。
4. **接管现有 Gradle 工程立项。** 让产品能把构建、验证、资产与恢复能力用在不是由它创建的 Fabric/NeoForge 工程上，去掉对 `.mcreator` 的硬依赖。范围和格式另行决定，本 ADR 只确定方向。
5. **数据包是一等工作区类型。** 契约、新建流程和文档把数据包与模组、资源包并列。缺少元素类型的内容用原始 JSON 加校验和游戏内重载验证来覆盖，不为每个注册表新做编辑器。
6. **流程按风险分级。** 不改变已发布产物的改动不走发布授权流程；发布节奏从按周改为按需；入库证据限于发布绑定所需，其余留在 `output/`。
7. **方向用同一套任务检验。** 每个阶段结束时重跑本次对照任务并加入游戏内行为断言；如果某项能力在两个阶段内都不能让 Copperbench 组在成功率、成本或验证深度上占优，就停止在它上面投入。

## 后果

- 需要改写内置对话指令、Agent 文档和首作教程；已有以元素为中心的教程保留为可选路线。
- 第一方 Fabric 生成器不再追求与 NeoForge 元素对齐；依赖某个元素类型的创作者在新轨道上可能需要改用原生代码。
- 同步上游 2026.3 的成本尚未评估，是第 3 项的前置工作。
- 验证回路成为主要工程投入：GameTest 模板、运行日志回传、数据包加载检查和资产预览的优先级高于新的编辑器。
- 既有的八轨证据、已发布版本的支持范围和兼容承诺不因本 ADR 改变。

## 未采纳的方案

- **继续追平上游的全部功能**：维护成本随版本线性增长，而上游已在补齐 MCP 等差异点。
- **停止项目，只用通用 Agent**：环境搭建、运行验证和资产可视化仍然没有现成替代，对不会编程的创作者尤其如此。
- **移除结构化层**：会破坏现有工作区和插件兼容；维护态已经能释放大部分投入。
