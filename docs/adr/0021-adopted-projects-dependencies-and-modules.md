# ADR-0021：接管工程第二阶段：模组依赖、多模块与多加载器

- 状态：提议，待项目所有者确认
- 日期：2026-11-28
- 细化：[ADR-0020](0020-adopt-existing-gradle-projects.md) 决定 9 与“已知限制”
- 待办落点：[维护清单第 11 项](../remaining-work.md#下一阶段方向调整)

## 背景

ADR-0020 的第一阶段已经实现，完成标准也已满足：对照实验的裸工程原样构建并通过验收；同一任务上，接管路线与 `.mcreator` 路线评分和验证深度相同，成本更低。按当时的决定，以下两类工程留到第一阶段验证之后再定。

**依赖其他模组的工程。** 按源码，打包 JAR 验收宿主（`GameTestSupport.host`）只做三件事：

- 把被测 JAR 放进宿主的 `run/mods`；
- 编译测试时只引用这个目录；
- 运行时只额外带上该轨道固定的加载器，以及 Fabric API 或 NeoForge。

工程声明的其他模组（例如用 `modImplementation` 引入的配置库）不会出现在宿主里，被测模组因缺少依赖而无法加载。

现在的出路是 `copperbench-tests.json` 的 `workspace` 模式：运行工程自己的测试任务，任务名可以带模块路径（如 `:fabric:runGameTest`）。这条路要求工程自己配好 GameTest，而且有两个缺口：

- 验收结果不绑定被测 JAR 的哈希；
- 不支持必需用例（`GAMETEST_REQUIRED_CASES_INVALID`），没有产品提供的隔离。

**多模块工程。** 识别规则是：

- `settings.gradle` 含 `include` 时记为 `GRADLE_PROJECT_MULTI_MODULE`；
- 同时带 Fabric 与 NeoForge 元数据时记为 `GRADLE_PROJECT_MULTI_LOADER`。

这两类工程可以打开、浏览和编辑，但不能构建和验收。验收用的产物也只在根目录的 `build/libs` 中查找（`GameTestSupport.artifact`）。

常见形态有三种：

- 一个模组加若干辅助模块；
- MultiLoader 模板（`common`、`fabric`、`neoforge` 三个模块）；
- Architectury（同样三分，用 Architectury Loom 插件）。

这三种形态在实际工程中各占多少，没有测量过。

## 决定（建议，待确认）

1. **验收宿主带上显式声明的模组依赖。**
   - `copperbench-tests.json` 新增 `hostMods`，列出要随被测 JAR 一起放进宿主 `run/mods` 的模组。每项是工程内的 JAR 相对路径，或 Maven 坐标加仓库地址。
   - 宿主编译测试时也引用这些模组。
   - 验收证据为每个附加模组记录来源和 SHA-256，与被测 JAR 一起绑定。
   - 传递依赖同样要列出；缺少时以加载器的报错说明缺什么。
   - Agent 可以按构建脚本填写 `hostMods`，开工摘要同时给出该字段的说明。
2. **支持只有一个加载器模块的多模块工程。**
   - 加载器模块指带 `fabric.mod.json` 或 `neoforge.mods.toml` 的模块。识别时在 `settings` 列出的模块里查找，版本与模组 ID 的读取规则沿用第一阶段（根目录与模块的 `gradle.properties`、元数据中的占位符）。
   - 构建用 `:<模块>:build`，产物取该模块的 `build/libs`。
   - 起步测试放在该模块的 `src/copperbenchTest`。
   - 不改写构建脚本、不为模块新增 Gradle 配置的原则不变。
3. **多加载器工程暂不进入第二阶段。**
   - 等出现实际工程或测得需求后再定。
   - 届时的方向是：一次会话只以一个加载器为目标，目标记在 `.copperbench/workspace.json` 的 `settings` 中、可以切换；每个目标各自构建和验收；公共模块的改动需要分别验收。
4. **检验方式沿用 ADR-0019 决定 7。** 每一项都用一个真实形态的工程完成构建与验收，并在同一任务上记录 Agent 的成本与验证深度：
   - 第 1 项：一个依赖常见配置库的 Fabric 工程；
   - 第 2 项：一个带辅助模块的工程。

## 后果

- 测试配置多一个字段，验收证据多一组附加模组；旧配置不受影响。
- 依赖多的工程仍可选择 `workspace` 模式，两条路并存。
- 第 2 项需要识别器、构建参数、产物位置和起步测试位置都按模块处理；会话、元数据和恢复点仍以工程根目录为单位。
- 多加载器工程在第二阶段仍只能浏览和编辑，原因照旧显示在总览页和诊断中。

## 未采纳的方案

- **自动读取工程的依赖。** 用产品的 init 脚本解析工程的运行时类路径（Loom 的 `modRuntimeClasspath`，ModDevGradle 则要逐个判断哪些是模组），不需要修改文件。不采纳的原因有三：
  - 它要在工程的构建里执行产品代码；
  - 各构建插件的配置名不同；
  - 会把工程的开发期依赖（如模组菜单、调试工具）也带进验收，验收结果因此依赖开发环境。

  显式声明更容易审阅，也能写进证据。
- **在构建脚本中加入测试依赖或产品插件。** 违反 ADR-0020 决定 2。
- **一个会话同时以两个加载器为目标。** 任务、诊断、环境和验收证据都要成对处理。在需求得到确认之前，成本过高。

## 需要确认的选择

- A. 依赖来源：显式 `hostMods`（建议）或自动读取。
- B. 第二阶段的范围：依赖与单加载器多模块（建议），或者同时做多加载器。
